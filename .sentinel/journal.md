## 2024-05-24 - [Path Traversal in GodotSaveService]
**Vulnerability:** Path Traversal vulnerability in `GodotSaveService.cs` allows arbitrary file writes/reads outside the intended `Save/` directory.
**Learning:** Using `ProjectSettings.GlobalizePath` removes Godot's internal virtual filesystem protections (`res://` or `user://`). When combined with raw string concatenation (`string path = m_saveDir + p_fileName`) and `FileAccess.Open`, it reintroduces standard OS-level path traversal exploits if `p_fileName` contains segments like `../../`.
**Prevention:** Always sanitize filenames using `System.IO.Path.GetFileName()` to strip directory path segments before appending them to the absolute save directory, and prefer `System.IO.Path.Combine()` over string concatenation.
## 2026-05-21 - [Verbose Exception Disclosure in API Middleware]
**Vulnerability:** The API layer's `ExceptionHandlingMiddleware` specifically targeted database exceptions (`SqlException` and `InvalidOperationException`), allowing other internal framework exceptions to bubble up unhandled. This could lead to a 500 error leaking native .NET stack traces and infrastructure details directly to the Web/Godot client in development environments or misconfigured production setups.
**Learning:** Relying on specific exception types for top-level middleware fails safely for databases, but leaves all other sub-systems (like JSON deserialization or network timeouts) exposed to framework-level crash disclosures. The API surface must have a definitive catch-all block that acts as a secure boundary, converting all unhandled exceptions into sanitized, opaque generic responses.
**Prevention:** Implement a global catch-all (`catch (Exception)`) at the highest layer of the request pipeline. Ensure the exception is securely logged locally using the standard logger, and substitute a generic 'Internal Server Error' payload for the external client response.
## 2024-05-22 - [SHA256 Checksum on Local Saves]
 **Vulnerability:** Unverified Godot save files allowing local data tampering and insecure deserialization.
 **Learning:** Godot's local `FileAccess` does not inherently protect against tampering. Standard fixes require generating sidecar checksum files (`.sig`) to safely verify integrity offline before deserialization.
 **Prevention:** All client-side local data storage implementations MUST generate and verify SHA256 signatures before reading sensitive JSON states into memory.
## 2025-02-14 - [Unsanitized string length constraints in text inputs]
**Vulnerability:** Text input fields (`UsernameField` and `PasswordField` in `LoginScreen.tscn`) lacked client-side and backend length constraints, potentially allowing excessive memory allocation and Denial of Service (DoS) attacks on the Web/BD API via arbitrarily long login strings.
**Learning:** Even if the database has its own constraints, failing to truncate inputs early on the Godot client and the core validator creates unnecessary strain on network and serialization pipelines, and opens up the backend to buffer issues when syncing credentials.
**Prevention:** Always enforce explicit `max_length` properties on UI input nodes (like `LineEdit`) in Godot and mirror these constraints exactly using C# constants (e.g., `MAX_USERNAME_LENGTH`) within the domain validation logic (e.g., `LoginValidator.cs`) to provide robust defense-in-depth.
## 2026-05-23 - [Unbounded length constraint on ExtraStats API payload]
**Vulnerability:** The `ExtraStats` field in `GameStats` is mapped to an `NVARCHAR(MAX)` column in the database to accommodate future flexible JSON payloads. However, the API endpoints (`PlayerController.Sync` and `StatsController.AddSession`) lacked input length validation for this field, allowing an attacker to bypass standard UI limits and inject multi-megabyte payloads, causing memory allocation spikes and a potential Denial of Service (DoS) attack against the server and database.
**Learning:** Flexible or schema-less columns (like JSON strings) in EF Core often bypass strict `[MaxLength]` validation constraints unless explicitly enforced. The flexibility of `NVARCHAR(MAX)` becomes a critical DoS vector if the ingestion boundary (API Controller) trusts the payload size blindly.
**Prevention:** Always implement strict maximum length validation checks explicitly within the API Controller methods for any incoming payload field that is mapped to a high-capacity or unbounded data type in the database.
## 2026-05-31 - [API String Length Validation on SyncRequest]
**Vulnerability:** The API DTOs `GameStats` and `InventoryEntry` lacked explicit data annotations for string lengths, relying solely on manual conditional logic or leaving properties unbounded, which risks buffer overflow and DoS attacks through excessive JSON payload injection during synchronization requests.
**Learning:** `NVARCHAR(MAX)` flexibilities in the database or lack of model definition sizes expose API controllers if they don't explicitly reject massive inputs. Manual string length checks are prone to being skipped or missed for newer fields. Relying on DataAnnotations automatically validates inputs upstream when `[ApiController]` handles the request model.
**Prevention:** Always attach `[StringLength(MAX)]` and other DataAnnotations onto all string properties in Domain DTOs that serve as external API inputs to lock down size constraints securely.
